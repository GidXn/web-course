### 3.3. URL, сформований власноруч (з параметрами запиту та фрагментом)
`https://gidxn.github.io/web-course/about.html?ref=lab2&lang=uk#site-footer`

| Компонент | Значення | Передається на сервер |
|---|---|---|
| Схема | https | — |
| Хост | gidxn.github.io | Так (заголовок `Host`) |
| Порт | 443 (неявний) | — |
| Шлях | /web-course/about.html | Так |
| Рядок запиту (розбір) | `ref=lab2` (ключ `ref`, значення `lab2`); `lang=uk` (ключ `lang`, значення `uk`) | Так, повністю — сервер отримує рядок запиту цілком і сам вирішує, чи його опрацьовувати |
| Фрагмент | `site-footer` | **Ні** — фрагмент (все після `#`) обробляється лише браузером: він прокручує сторінку до елемента з відповідним `id` і на сервер не надсилається |

**Висновок:** сервер отримує схему опосередковано (через тип з'єднання), хост, порт, шлях і рядок запиту; фрагмент — суто клієнтська частина, потрібна лише для навігації всередині вже завантаженої сторінки.

## 6. Дослідження кодів стану

| Код | Приклад дії у браузері | Заголовки / пояснення |
|---|---|---|
| 200 OK | Завантаження `web-course/` при першому відкритті | Стандартна успішна відповідь, тіло документа передається повністю |
| 307 Internal Redirect *(замість очікуваного 301/302)* | Введення в адресний рядок `http://gidxn.github.io/web-course/index.html` | Перенаправлення на HTTPS відбулося, але **не від сервера**, а всередині самого браузера — див. пояснення нижче |
| 304 Not Modified | Повторне завантаження сторінки з увімкненим кешем | `if-none-match` запиту збігся з `etag` попередньої відповіді → сервер підтвердив, що вміст не змінився |
| 404 Not Found | Звернення на `https://gidxn.github.io/web-course/no-such-page.html` | `Content-Length: 5254` — GitHub Pages віддає власну стандартну сторінку 404, а не порожню відповідь |

**Чому 301/302 не з'явився, а замість нього — 307 Internal Redirect.** Це не помилка виконання, а правильно зафіксований і поясненний результат. У відповіді на запит `no-such-page.html` (код 404) присутній заголовок `Strict-Transport-Security: max-age=31556952` — сайт `gidxn.github.io` увімкнув **HSTS** (HTTP Strict Transport Security). Браузер, побачивши цей заголовок один раз, запам'ятовує (приблизно на рік, `max-age` у секундах) правило «завжди відкривати цей хост лише через HTTPS» — і за наступного звернення до `http://` він підмінює адресу на `https://` **ще до відправлення запиту на сервер**, що DevTools і показує як внутрішній (`307 Internal Redirect`), з приміткою `Non-Authoritative-Reason: HSTS`. Класичний серверний `301 Moved Permanently` тут в принципі неможливо побачити повторно — HSTS-заголовок «випереджає» його на боці клієнта. Це чудова ілюстрація механізму HSTS для звіту.

## 7. Дослідження механізму кешування

| | Обсяг переданих даних | Позначка кешу |
|---|---|---|
| Завантаження з увімкненим Disable cache | ≈ 996,3 KB | — |
| Повторне завантаження з вимкненим Disable cache | ≈ 994,4 KB | не позначено окремо на скріншоті |

**Економія трафіку (за сирими цифрами):** (996,3 − 994,4) / 996,3 × 100% ≈ **0,19%**.

**Чому економія виглядає такою малою — і чому це оманливо.** Обидва загальні обсяги (≈994–996 KB) майже повністю складаються з файлів стороннього розширення браузера (`content.css` — 307 kB, `sprite.svg` — 231 kB, кілька `*.js` — сотні kB), які завантажуються заново незалежно від кешу сторінки, бо це окрема логіка розширення, а не ресурси сайту. Тому загальна економія в 0,19% характеризує здебільшого поведінку розширення, а не ваш сайт.

Якщо розглянути **лише файли самого сайту** — `index.html` (1,2 kB) і `style.css` (881 B), сумарно ≈ 2,1 kB — картина інша: `index.html` отримав код **304 Not Modified** при повторному запиті, тобто тіло файлу взагалі не передавалося повторно (лише заголовки, ≈122 B за скріншотом). Це означає, що для власне ваших двох файлів економія практично **близька до 100%** — сервер підтвердив валідність кешу за `ETag`/`If-None-Match`, і браузер використав збережену копію.

**Заголовки кешування головного документа:** `Cache-Control: max-age=600` (10 хвилин, доки браузер вважає копію свіжою без запиту на сервер), `ETag: W/"6ab4e12e-afb"` (слабкий валідатор вмісту — слово "W/" означає, що порівнюється смислова еквівалентність, а не побайтова), `Expires: Thu, 24 Sep 2026 09:26:07 GMT` (дублює семантику `max-age` для сумісності зі старими клієнтами). Заголовок `Last-Modified` у захопленні відсутній — GitHub Pages/Fastly для цього сайту покладаються саме на `ETag`, а не на дату модифікації.

**Висновок:** сторінки GitHub Pages кешуються за замовчуванням (`max-age=600` + валідація через `ETag`), тож для повторних візитів реальний обсяг переданих даних вашого сайту мінімальний; отриману в захопленні цифру економії 0,19% коректно інтерпретувати саме як «економію для вкладки в цілому, викривлену стороннім розширенням», а не як показник ефективності кешування самого сайту.

## 8. Дослідження захищеного з'єднання

| Параметр | Значення |
|---|---|
| Емітент сертифіката | вказано в панелі як «YR1» — короткий підпис проміжного центру сертифікації Let's Encrypt (для точної назви відкрийте «Open full certificate details») |
| Суб'єкт (Subject) | `*.github.io` |
| SAN (альтернативні імена) | `*.github.com`, `*.github.io` та ще 6 записів (всього 8) |
| Термін дії | з 02.08.2026 по 31.10.2026 (≈ 90 днів — типовий короткий термін дії сертифікатів Let's Encrypt) |
| Версія TLS | **TLS 1.3** |
| Обмін ключами | X25519MLKEM768 — гібридна схема, що поєднує класичний X25519 із постквантовим алгоритмом ML-KEM-768 (захист на випадок майбутніх атак квантовими комп'ютерами) |
| Підпис сервера | RSA-PSS with SHA-256 |
| Шифр | AES_128_GCM |
| Заголовок Strict-Transport-Security | **Присутній** (`max-age=31556952`, ≈ 1 рік) — знайдений у Network → Headers відповіді на запит `no-such-page.html`; у панелі Security він не відображається, оскільки це заголовок відповіді, а не атрибут сертифіката |

**Certificate Transparency:** сертифікат зафіксовано у двох незалежних публічних журналах (Google «Argon2026h2» і Let's Encrypt «Willow2026h2»), обидва підписи вбудовано в сертифікат і верифіковано браузером — це підтверджує, що сертифікат публічно видимий і не міг бути виданий приховано зловмисником.

**Висновок:** з'єднання захищене сучасним протоколом TLS 1.3 з підтримкою постквантового обміну ключами, короткоживучим (90-денним) сертифікатом від Let's Encrypt та увімкненим HSTS — усе це відповідає актуальним практикам безпеки для статичного хостингу GitHub Pages.

## 10. Висновки

Сайт‑візитка відповідає вимогам до **легкого статичного проєкту**: мінімальний обсяг, сучасні протоколи, ефективне кешування та захист. Основні проблеми Lighthouse‑аудиту виникають не через сам сайт, а через **сторонні розширення браузера**, які спотворюють результати вимірювань. Тому ключовий практичний урок: **аналіз продуктивності слід проводити у контрольованому середовищі** (чистий профіль або інкогніто), щоб отримати достовірну картину роботи власного проєкту.
